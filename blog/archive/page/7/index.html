Features and Feature Stores — Where Fraud ML Is Actually Won

Ask practitioners where fraud detection quality comes from and the answer is uniform: not the model — the features. Velocities, histories, graph signals, and their freshness carry the signal; the model just reads it. And ask where production fraud ML fails and the answer is equally uniform: the gap between how features were computed in training and how they're computed at serving time. This post covers both — the feature families that catch fraud, and the feature-store discipline that keeps them honest.

Signal lives in velocities (second-fresh streaming aggregates), histories, precomputed graph neighborhoods, and composed scores. The characteristic failure is training/serving skew — feature time-travel leaking the future into training. The feature store fixes it by construction: one event-time definition, two materializations.

Selective Test Execution — Running Only the Tests a Change Can Break

The single highest-leverage move against suite collapse is refusing the premise: a change touching one module does not need the whole suite — it needs the tests that could plausibly fail because of it. Selecting that subset correctly, from dependency structure rather than hope, is how 50-million-line codebases keep CI in minutes. The engineering is in the word "correctly": an over-selective system merges breakage; an under-selective one buys nothing.

Run the reverse transitive closure of a change — via build graphs, extracted dependencies, or coverage maps — while honestly engineering the escapes: annotated invisible edges, a post-merge full-suite safety net whose misses are selection bugs, and a measured escape rate. Selection + caching + sharding is the monorepo formula.

Build Systems — Fast and Correct Are the Same Investment

Every DevProd capability this series described stands on one foundation: a build system that is fast because it is correct. Caching that can be trusted, selection that can be sound, codemod fleets that can be verified — all of them require builds whose inputs are fully declared and whose outputs are reproducible. The old framing treats speed and correctness as a trade-off; modern build engineering discovered they're the same property, bought once: hermeticity.

Hermeticity is the one property — declared inputs, enforced graphs, deterministic outputs — from which sound caching, correct selection, remote execution, and supply-chain attestability all follow. Fast and secure are the same investment; earning it on a grown codebase is an org-loop campaign worth running at scale.

The denoiser is secretly learning the score — the gradient of log-probability pointing toward more-plausible images. Thin Events, Fat Events — Payload Design and the Fetch-on-Event Pattern

Every webhook program eventually argues about payload shape: send the whole resource ("fat"), or just an ID and a hint ("thin")? The argument feels stylistic and is actually architectural — it decides your staleness semantics, your security exposure, your versioning burden, and whether consumers converge on truth or drift from it. This post makes the trade explicit, explains why providers have been drifting thin, and locates the pattern most receivers should default to: the event as doorbell, the API as truth.

Fat events are self-contained but stale-by-construction, data-exposing, and a second API to version; thin events are doorbells whose fetch returns authorized current truth and dissolves ordering problems. Default: doorbell, queued fetch, version-gated upsert — fat for immutable facts, thin for mutable state.

Rules and Models — Why Fraud Systems Need Both

Every few years someone declares rules dead — just let the model learn everything — and every production fraud team quietly keeps both, because rules and models are good at different, complementary things: rules deploy in minutes against the attack happening right now, encode hard policy exactly, and explain themselves completely; models find the subtle multidimensional patterns no human would write down. The engineering question isn't which — it's how the two compose into one decision.

Rules deploy in minutes against live attacks, encode policy exactly, explain themselves completely, and hold the blind spots; models (GBDTs as the tabular workhorse) own the unstateable patterns. Composition makes them one decision: policy first, scores next, cost-thresholded logic last — versioned and golden-tested.
