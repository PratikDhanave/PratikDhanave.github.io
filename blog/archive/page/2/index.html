Specs and SDKs — Making the Contract Machine-Readable and the Clients Generated

An API that exists as code, a spec document, hand-written SDKs in six languages, and documentation pages is an API that exists in four slowly diverging copies. The evolution-era answer is to pick one source of truth — the machine-readable spec — and generate or verify everything else from it, so a change made once propagates everywhere or fails loudly. This post is the spec-first pipeline: what it takes, what it buys, and where generated SDKs still need human hands.

One machine-readable source of truth: complete specs, bidirectional conformance tests, dated snapshots per version, and spec-diff breaking-change detection as the evolution linter. Generate the mechanical 80% of every SDK with tolerant-reader behaviors built in; humans keep idiom and the fenced hand-written islands.

Model Evolution I: Learning Without Gold Answers

The deepest locus of self-evolution is the weights — and the interesting frontier there is not supervised fine-tuning on human labels but the family of methods where the model improves from signals it generates or uncovers itself: pseudo-labels from its own consensus, rewards from self-play, curricula it proposes to itself. This post organizes that family by one question — where does the training signal come from when no gold answer exists — and traces the shared failure mode every branch inherits: a model learning from itself can amplify its knowledge, and can just as efficiently amplify its errors.

Label-free weight evolution sorted by signal source: consensus as pseudo-truth (sharpens knowledge, launders bias), self-play as curriculum (risks private equilibria), verifier reward (internalizes verifier exploits), environment signal (honest, slow, governance-heavy). Learning from Experience — Procedural Memory and Agents That Get Better

Everything before this post helps an agent remember; this one asks whether it can improve. The difference is procedural: an agent that recalls last week's failed deploy has memory, while an agent that deploys differently because of it has learned. Procedural learning is the highest-leverage loop in agent engineering — every improvement compounds across all future tasks — and the most dangerous, for exactly the same reason. The craft is building the loop with brakes.

Learning without weight changes lands in artifacts: rules, playbooks, worked examples, failure memory. The loop breaks at misattribution, overgeneralization, rot, and conflict — and procedural writes deserve deploy-grade brakes: proposal review, provenance, blast-radius scoping, regression evals. Start with failure memory and worked examples; they compound at a fraction of the risk.

Invoicing and Collection — From State to Document to Money

The invoice is where billing's abstractions become a legal document and an attempted charge. Everything upstream — price versions, metered totals, prorations — converges into line items a human must be able to read and a regulator must be able to audit; then the system has to actually collect, which means confronting the fact that a meaningful fraction of payments fail. Invoicing is document engineering; collection is failure engineering; revenue requires both.

The invoice is an immutable derivation — re-derivable from versioned inputs, frozen at finalization, corrected only by new documents. Collection is failure engineering: dunning that distinguishes hard from soft declines, schedules retries deliberately, and treats the payment-update email as part of the machinery.

Memory as Tools — Paging, Files, and Agents That Manage Their Own Minds

Everything so far treated memory as plumbing the harness operates around a passive model. The most interesting turn in recent agent design flips that: give the model tools to read, write, and reorganize its own memory, and let it decide what's worth keeping. The operating-system analogy arrived early — a small, fast context window backed by a large, slow store, with something paging between them — and it keeps paying dividends. This post covers agentic memory: the OS view, file-based memory, and consolidation.

The agentic turn: context as RAM, store as disk, the model participating in paging policy — plus file-based memory as the transparent, diff-reviewable baseline, and consolidation as the background process that extracts facts, distills lessons, and revises standing memory. The consolidator is the highest-privilege writer in the system; review and evaluate it like one.
